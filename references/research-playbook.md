# 北京共同居住选址研究手册

## 1. 建立需求卡

至少保留下列字段：

| 字段 | 内容 |
| --- | --- |
| 成员/工作地点 | 地址、地图坐标、办公入口 |
| 出行方式 | 摩托车、地铁、公交、驾车、步行 |
| 通勤时段 | 上班和下班大致时间 |
| 通勤上限 | 单程可接受时长、可接受总路程 |
| 硬排除 | 小区、街道、房屋属性或通勤条件 |
| 租赁预算 | 月租、额外费用、押付和租期 |
| 房屋要求 | 两居、面积、楼层、朝向、电梯、民水民电燃气 |
| 生活偏好 | 地铁、超市、公园、医院、停车、安静、绿化 |

硬排除优先于所有评分。例如用户明确排除某小区后，不能再以便宜、环境好或路程短为由恢复推荐。

## 2. 地图与路线

### 候选坐标

1. 对住址和工作地点分别地理编码或搜索 POI。
2. 同名地点必须用行政区、地图坐标和用户描述校对。
3. 记录候选小区出入口与实际楼栋的关系；大型小区不能只用社区中心点。

### 通勤比较

- 摩托车：按可行路线记录距离、时长和主要道路，提示禁行与快速路策略无法完全模拟。
- 驾车：记录常规路线、备选路线、拥堵节点、收费和停车成本。
- 地铁/公交：记录步行到站、换乘次数、首末班和故障替代方案。
- 所有时间都标注“平台预测、实测、住户反馈或推断”。

### 高峰判断

1. 若接口支持未来出发时间或交通预测，按用户实际时段查询并保存查询日期。
2. 若驾车 Web 服务只返回当前/常规路线，不把普通导航时间标成早晚高峰。
3. 用平台高峰预测、路线流量特征、住户反馈或多次实测补足，并给出合理区间。
4. 最终建议使用保守时间，例如“常规 30 分钟，高峰 40–55 分钟”，避免虚假精度。

## 3. 租赁市场

- 搜索在租房源、成交或指导价、同小区近期房源。
- 优先记录具体房号/户型线索和发布时间；无法确认是否仍可租时标注“历史/待核验”。
- 计算真实月成本：租金 + 物业费 + 停车 + 常见通勤交通费。
- 注意商住、公寓、loft、民水民电、燃气、产权年限和供暖方式，逐套确认。
- 低于市场明显较多的报价可能是虚假房源，不能直接据此宣布预算达标。

## 4. 社区口碑

建议按以下维度检索，并保留正反两面：

| 维度 | 典型关键词 |
| --- | --- |
| 居住舒适 | 噪音、采光、隔音、漏水、电梯、供暖 |
| 物业服务 | 报修、门禁、垃圾、绿化、物业响应 |
| 车辆管理 | 车位、停车费、乱停、锁车、充电 |
| 周边生活 | 超市、菜场、学校、公园、医院、餐饮 |
| 租住体验 | 中介、押金、房东、维修、租售纠纷 |
| 通勤 | 地铁、公交、堵车、限行、早晚高峰 |

证据权重依次为：近期多条真实住户反馈 > 近期单一住户反馈 > 多个平台转载 > 旧反馈 > 中介宣传。单帖可以提示风险，但不能单独决定分数。

## 5. 安全与合规

- API Key 不进入版本控制；推荐读取 `AMAP_WEB_API_KEY`，命令行传参时避免展示完整值。
- 不抓取需登录才能查看的私人数据，不绕过验证码。
- 尊重平台服务条款，记录来源和访问限制。
- 不提供虚假、未经核验的“网友评价”；无法访问正文时只陈述可见摘要并标注限制。
